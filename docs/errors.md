# Problem Details

All application-generated error bodies use RFC 7807 and `Content-Type: application/problem+json`. The body is the problem object itself, without an error envelope. HTTP headers such as `WWW-Authenticate` and `Allow` remain authoritative.

Ledger always includes `type`, `title`, `status`, `detail`, and `instance`. The full type URI is the stable machine identifier. Titles are fixed English summaries; detail describes the occurrence safely. Status equals the HTTP response status. Instance is a server-generated `urn:uuid:<UUID>` correlated with a structured log entry. Clients should branch on type, not parse title/detail. Unknown extension fields should be ignored.

```json
{
  "type": "https://ledger.ztd.me/errors/api-version-unsupported",
  "title": "Unsupported API version",
  "status": 400,
  "detail": "The requested API version is not supported.",
  "instance": "urn:uuid:4ef176ce-6c0f-4a0f-a826-23dfc4938d63",
  "supported_versions": ["2026-09-16"]
}
```

Every slug below has the prefix `https://ledger.ztd.me/errors/`. Type URIs do not contain the major version or contract date. Never reuse a type for different semantics; introduce a new type instead. These URIs identify documentation; the application does not fetch them, and this phase does not publish pages to the domain.

| Status | Slug | Meaning |
| --- | --- | --- |
| 400 | api-version-required | Header absent for a recognized API major |
| 400 | api-version-invalid | Header empty, repeated, or not a canonical calendar date |
| 400 | api-version-unsupported | Well-formed date unsupported for this major; includes supported_versions |
| 400 | invalid-request | Invalid body or parameters |
| 401 | authentication-required | Missing Bearer session token |
| 401 | invalid-token | Malformed, expired, untrusted, or otherwise invalid session token |
| 403 | user-disabled | Local user is disabled |
| 403 | access-denied | Inactive tenant/member, insufficient privileges, or forbidden administrator change |
| 404 | api-major-version-unsupported | API path major not registered |
| 404 | not-found | Resource or route absent, including resources outside the authorized tenant |
| 405 | method-not-allowed | Method not supported; includes Allow |
| 409 | bootstrap-required | Authenticated identity has no local initialization |
| 503 | service-unavailable | HTTP-only business request, unavailable verification keys, or failed readiness |
| 500 | internal-error | Unexpected application failure |

Field-level validation can include an `errors` array with `location` (`body`, `path`, or `query`), `name`, and `reason`. It never echoes raw values. Generic malformed bodies may omit field errors. For example:

```json
{
  "type":"https://ledger.ztd.me/errors/invalid-request",
  "title":"Invalid request",
  "status":400,
  "detail":"Request parameters are invalid.",
  "instance":"urn:uuid:4ef176ce-6c0f-4a0f-a826-23dfc4938d63",
  "errors":[{"location":"body","name":"timezone","reason":"An IANA timezone is required."}]
}
```

Do not log bearer tokens, raw queries, upstream error payloads, or panic values. The shared responder logs instance/type/status at WARN for 4xx and ERROR for 5xx, with a sanitized underlying cause when available; clients still receive only a generic detail for unexpected failures. Panic recovery emits a problem only before the response is committed; an already-started response cannot be replaced. Errors generated by an upstream proxy or the HTTP transport before application dispatch are outside this application contract.

With Sentry enabled, non-panic 5xx problems create one issue and expected 4xx responses remain logs. Panic capture is owned by sentrygin; the Problem Details fallback does not capture it a second time. The server-generated X-Request-ID correlates access logs, Sentry and the response. See [observability](observability.md).
